# مخطط Backend مستقبلي

هذه الوثيقة توصية مبدئية وليست تنفيذًا أو التزامًا بمزود بعينه.

## مكونات مقترحة

1. REST API موثق بعقود versioned ومطابق لـZod schemas الحالية.
2. قاعدة بيانات علائقية لحفظ التصنيفات والثيمات والمراجعات والطلبات والتراخيص.
3. لوحة إدارة محمية لنشر الثيمات وتحديث الأسعار والمحتوى وحالة التوافق.
4. object storage خاص لملفات الثيمات والصور الأصلية، مع فحص الملفات وsigned URLs قصيرة العمر.
5. طبقة دفع server-side مع مزود متاح قانونيًا وتجاريًا للسوق المستهدف.
6. مهام webhook للتحقق من الدفع وتسوية حالة الطلب وتفعيل استحقاق التنزيل.

## ضوابط أمنية وتجارية

- لا تثق في السعر أو `themeId` أو الإجمالي القادم من العميل؛ أعد الحساب على الخادم من نسخة السعر الحالية.
- لا تخزن بيانات البطاقة. استخدم صفحات/حقول مزود الدفع المستضافة حسب المتطلبات.
- تحقق من webhook signature ومنع إعادة تشغيل الحدث قبل تغيير حالة الطلب.
- لا تصدر ملفًا قابلًا للتنزيل قبل التحقق من حالة الدفع والترخيص، وسجّل عمليات التنزيل.
- استخدم rate limiting وvalidation وaudit logs، واحمِ لوحة الإدارة بصلاحيات واضحة.
- راجع سياسة الخصوصية والاحتفاظ بالبيانات وحقوق الملكية الفكرية وشروط البيع والاسترجاع.
- لا تستخدم شعار سلة أو تصف متجرًا بأنه معتمد منها من دون تفويض موثق. راجع شروط ووثائق سلة الحالية لأي تكامل؛ لا تستخدم scraping ولا تخترع endpoints.

## انتقال تدريجي

1. استبدال mock transport بخدمة HTTP للكتالوج مع بقاء الواجهة وعقودها ثابتة.
2. إضافة حسابات وجلسة آمنة فقط إذا تطلب المنتج ذلك، مع مراجعة إدارة الهوية.
3. بناء سلة خادمية وأسعار مُثبتة عند إنشاء الطلب.
4. إدخال payment provider عبر backend، ثم اختبارات sandbox وwebhook.
5. إصدار ترخيص/استحقاق تنزيل بعد التأكيد الخادمي فقط.
6. تحويل demo ratings والـfixtures إلى بيانات حقيقية موثقة، وإزالة أي مؤشرات تجريبية بعد المراجعة.
